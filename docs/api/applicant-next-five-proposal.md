## FE-08: identity and sessions

Reuse Go-owned opaque hashed-token cookies, exact Origin, synchronizer CSRF, bounded JSON, safe errors and no-store. Next forwards only intended cookie/headers to the configured loopback API. An applicant session cannot satisfy any existing privileged guard; a privileged account cannot be changed or authenticated by requesting an applicant email code, even when emails match. No password/reset-password or role selection for applicants. No client storage authentication.

Proposed schema is additive: separate `applicants`, applicant session subject/FK and purpose-bound OTP challenges. Preserve privileged account/session checks and existing rows. The exact migration and schema gate must be reviewed after contract approval, with generated sqlc output and owner-run disposable migration/forward-recovery verification. Do not simply extend `accounts.role`: its required password/TOTP and bootstrap assumptions are privileged-only.

Normalize email consistently with the existing lowercase identity convention; initial scope bounded ASCII email addresses, at most 254 characters, reject display names/controls/multiple addresses. Do not collapse dots, strip plus tags or silently link accounts. Internationalized identities require a later explicit contract. Challenge identifiers and codes are cryptographically random; return no code, email-existence flag or account details. Use a keyed digest bound to challenge/purpose/identity for low-entropy OTPs; never store bare codes or an unkeyed six-digit digest. Key handling must reuse protected configuration without exposing bytes or weakening ACL checks.

Recommended limits: six digits, ten-minute expiry (at the exact boundary expired), five failed verifications per challenge; resend after 60 seconds invalidates the previous challenge/code. Maximum five sends per normalized identity/hour and twenty per peer/hour; additionally bound challenge verification attempts per peer and identity to twenty/hour, independent of resends. Store counters transactionally, including rejected attempts. Initial applicant session seven days absolute, 24 hours idle; rotate on successful verification, revoke on logout/deletion. Anonymous sessions and privileged pending/full lifetimes remain as implemented. Expired state never silently becomes authenticated. Limits and cleanup must survive process restarts. Operator terminal delivery is an explicit development exception only; no codes in frontend, URLs, response bodies, tracing or general logs. Fake senders in offline tests retain synthetic codes only in test memory.

## FE-09: profile, files and deletion

Proposed routes: GET/PATCH `/applicant/profile` (name, email/phone contacts, optional location/bio and expected version); POST `/applicant/cv` (bounded multipart upload); GET `/applicant/cv` (authenticated attachment stream); POST `/applicant/cv/remove` (CSRF/version); POST `/applicant/deletion/request` and `/applicant/deletion/confirm` (fresh purpose-bound email challenge, then explicit confirmation). All infer owner from server session; no owner ID in request payload. Editable contact email is not login-email replacement; identity change remains out of scope. Minimum name two Unicode characters, maximum 100; at least one valid contact, email at most254, phone at most32, bio at most2000; optional location must reference an active location. Review these proposed bounds before code.

File cap exactly 5,242,880 bytes enforced while streaming (plus small bounded multipart overhead); reject legacy `.doc`, mismatched extension/content, encrypted/uninspectable content and malformed archives. Validate PDF structure with a reviewed parser, not just a magic prefix. `.docx` must be a valid bounded OOXML ZIP with expected content types/document, no macros, traversal, symlinks, executable payloads or external relationships; bound entries and total expanded bytes before decompression. Parser/scanner dependencies require separate justification/pins through the existing dependency policy. No newly chosen dependency here.

Private storage keys generated by server, separate from user filenames and outside public/build roots; never return filesystem paths/public URLs. Downloads require current own-data authorization, no-store, attachment disposition, sanitized filename and nosniff; staff/company access is a later separately authorized route, never this endpoint. Record only permitted IDs/times in audit. Upload to quarantine, validate/scan with strict time/resource bounds, then atomically switch profile pointer; failed replacements leave old CV intact and remove staged artifacts. Unknown scanner state fails closed. Application CVs are immutable independent snapshots, unaffected by profile replacement/removal. Crash recovery must reconcile staging/DB/deletion intents without resurrecting a file.

Deletion must revoke sessions/access and redact profile/contact in the same transaction that persists deletion intent; purge private profile bytes before returning a completed result. Failures return an honest pending state until bytes are removed, with monitoring/retry and no restored access. No fake immediate-success response. Retention worker and request-time authorization enforce expiry even if scheduler is down. Deletion tombstones are IDs/times only and re-applied during restore; restore drill and backup maximum 35-day expiry evidence required before real intake. Audit lifetime remains a policy gate, not indefinite retention. No backup or purge execution authorized by these specifications.

## FE-10: on-site applications

Proposed GET `/applicant/jobs/{jobId}/eligibility` returns current job/method/expiry, active recruitment authority, required documents and approved consent version; POST `/applicant/applications` accepts `{jobId,profileVersion,cvVersion,consentVersion,accepted:true,idempotencyKey,website:""}` (empty hidden trap) and returns201 only after committed acceptance. Retrying an identical accepted submission returns200 with the original record; a unique applicant/job conflict gives409 `already_applied` with only the caller's record reference. Exact expired boundary rejects; external methods never create an application.

Transaction locks job/authority, rechecks published status, expiry, authority validity, active applicant/profile/CV/consent version and duplicate/idempotency constraints. Create immutable snapshot, Submitted record, actor/time audit and outbox event as one coherent operation. Private bytes may stage before the DB transaction but must never become an accepted/publicly accessible snapshot on failed commit; reconcile orphan staging. Serialize deletion/submission and authority-revocation/submission races; the loser must fail safely. Do not hold DB locks during arbitrary upload/scan/provider calls. IDs in snapshots must support later retention without persisting deleted profile contacts beyond approved timelines.

**Hard dependency outside these five tasks:** FE-14 live employer recruitment-authority administration, evidence/revocation rules and public warning/report/content safeguards. A verified company badge alone is insufficient. Keep current live on-site publish/intake blocked until FE-14 plus privacy/scanner/retention safeguards are accepted. Disposable fixtures may exercise the endpoint under owner-run tests; a hidden operator SQL toggle is not an authority-management substitute. No real applicant testing, new application rows or job publication authorized now.

## FE-11: own applications and notifications

Proposed GET `/applicant/applications?page&pageSize`, GET `/applicant/applications/{id}`, GET `/applicant/notifications?page&pageSize`, POST `/applicant/notifications/{id}/read` with CSRF/version. Infer applicant ID server-side on every query. Foreign/missing/deleted IDs return the same404; no company/staff view through these routes. Maximum pageSize50; validate duplicate/unknown query keys and stable sort by creation timestamp plus opaque ID. Return empty arrays for real empty data;503 for service failure. No shared private cache or arbitrary object URL.

Projection: application ID, job/company public label, submitted timestamp, current stage and permitted stage timestamp history; interview start/timezone/location or safe joining instructions, explicit cancelled/rescheduled state. Do not return internal notes, staff contact, other applicants, sharing internals or CV storage keys. Retained copies from deleted accounts have no applicant-facing session. No withdrawal/export/saved-job feature. Stale links and expired jobs do not invent new outcomes.

Store stage/interview event and notification/outbox atomically; display events only from authorized server writers, never user-submitted stage names. Dispatcher uses bounded retries/backoff, idempotency per event/recipient/channel and terminal failure status for operator review. Recheck account state, retention and current recruiter assignment at send time; after deletion cancel queued messages without copying deleted contact into audit/errors. External email is at-least-once: provider idempotency is needed to minimize duplicates after uncertain delivery, never promise exactly-once sending. Mark-as-read is idempotent and does not delete the underlying event. Actual provider dispatch and staff writers remain separately gated.

## Compatibility, verification and delivery order

1. Approve identity/delivery/OTP/session contract; implement FE-08 development slice and preserve all privileged regression checks.
2. Approve file validation/storage/consent/deletion boundaries; implement FE-09 with own-data, crash/restore/retention evidence before real intake.
3. Approve application policies and complete FE-14 authority safeguards; implement FE-10 with private snapshots, races and outbox atomicity. Development test readiness is separate from real intake activation.
4. Implement FE-11 own-data reads/in-site updates; enable actual email only after provider approval. Do not fabricate stage changes to make a demo appear live.
5. Use FE-12's [remaining-panel design](../design/admin/remaining-panels.md) to specify later writers/projections; design can progress while the above services are gated.

Use existing Go/Next/pgx/sqlc/migrate architecture; no second auth service, database client in Next or new dependency selected. New schema numbering/gates and downgrade risks must be documented before migration source changes. Migrations are additive and owner-applied; forward repair or reviewed owner backup recovery preferred. Never down/drop/reset real data. Existing accounts/jobs/lists/FKs/seeds retained.

Future meaningful checks: OTP expiry/resend/replay/rate-limit races and purpose/role isolation; cross-applicant ID/file denial; content/size/ZIP/quarantine/crash cases; deletion/submission/worker/restore races and month-end/leap dates; duplicate/idempotent/authority/expiry submission races; own-data pagination/notification read state and retry/delete suppression; role/company/assignment denial. Use established offline Go tests/vet and integration compile, existing frontend unit/lint/build/typecheck and synthetic HTTP suites, then owner-run disposable migration/integration and observed browser journeys at 375/768/1440. No future behavior is passed by drafting these contracts. Independent review, owner acceptance and separately authorized release remain required.
